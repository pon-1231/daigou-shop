# 真實資料回測報告，以及一件必須先講清楚的事

你要求兩件事：**把盈虧比拉小、固定成 1:2R**，以及**用今年（2026）的資料回測**。
第一件事做完了。第二件事**做不到**——不是我不想做，是這個沙盒環境的網路權限
不允許。下面誠實交代發生了什麼、我實際測了什麼、以及這些數字能不能信。

---

## 1. 為什麼沒有「今年」的資料

這個 session 的對外連線被組織政策鎖死，**只允許 GitHub 網域**
（`raw.githubusercontent.com` 這類存放公開檔案的 CDN；`api.github.com` 還被
限制在你授權的這一個 repo 範圍內）。我實際測試過的結果：

| 來源 | 結果 |
|---|---|
| stooq.com | 連線被組織政策擋（403） |
| Yahoo Finance API | 被擋（EGRESS_BLOCKED） |
| Hugging Face / Google Drive | 被擋 |
| histdata.com | 被擋 |
| GitHub 上找得到的「近期／每日更新」黃金 M15 資料集 | 檔案是 **Git LFS 指標檔**（真正的資料在 LFS 儲存，這個沙盒的匿名讀取管道抓不到，只能拿到一個 133 bytes 的指標文字） |
| 直接 `git clone` 第三方 repo 來讀資料 | 被 Claude Code 的自動模式分類器擋下（歸類為「不受信任的程式碼整合」，即使我只想讀資料不執行程式） |
| 券商 MT4/MT5 即時報價 API | 這個環境本來就沒有對外的券商連線 |

所以：**不是我偷懶用假資料交差，是這條路在這個環境裡目前被物理性地堵住了。**
第 6 節會講怎麼繞過這個限制——答案是需要你動手匯出一次。

## 2. 那我實際測了什麼

我在 GitHub 上找到一份**真實的**（不是合成的）XAUUSD M15 資料，可以透過
`raw.githubusercontent.com`（非 LFS）直接抓到完整內容：

- 230,400 根 M15 K 棒，**2012-05-15 → 2022-03-04**，約 10 年
- 我做了兩項驗證，確認它是真實市場資料而不是垃圾：
  1. **價格範圍對得上歷史事實**：2012 年約 $1550/oz，2022 年約 $1970/oz，
     跟黃金這十年的實際走勢一致。
  2. **波動率的時段分佈對得上真實市場結構**：我用每小時平均波幅畫出一天 24
     小時的波動曲線，波峰落在原始時戳的 15:00–17:00——這正是「紐約開盤」
     該出現的位置，**如果**這份資料用的是 UTC+2/+3 的券商時間（歐洲常見
     的 MT4/MT5 伺服器時區）。我因此**假設**來源時區是 `Europe/Athens`
     （UTC+2，夏令時 UTC+3）。

**這個時區判斷是用波動率形狀反推的，不是有文件保證的事實。** 這代表
killzone 的判定可能有系統性的偏移（可能到一小時），這在下面的結果解讀裡
會一直提醒你。這也是為什麼「用真實資料就能信」這句話本身需要再往下細分——
連資料的時區都需要驗證，這正是這類系統最容易被忽略、也最致命的錯誤來源
（見 `docs/METHODOLOGY.md` 第 2.2 節）。

原始資料只有 M15（沒有 M5），所以這次測試把執行時框從預設的 M5 **改成 M15**，
中時框改成 H1、高時框維持 H4。設定檔存在
[`config/xauusd_m15_real_1to2R.json`](../config/xauusd_m15_real_1to2R.json)。

## 3. 1:2R 的改動

三個劇本原本用「盈虧比拉到下一個流動性池」（`target_mode="draw"`），
賠率因劇本而異（1.8–2.5，且理論上可以更高）。改成你要的：

```python
target_mode="rr"
fixed_rr=2.0
min_rr=2.0
```

固定 1:2R，三個劇本一致。這個改動的取捨很直接：**犧牲「跟著市場給多少拿多少」
的彈性，換來「每一筆的數學期望值結構完全相同」**——這是能不能累積出乾淨樣本
的前提，也是你要求的方向。程式碼在
[`ictgold/config.py`](../ictgold/config.py) 的 `default_setups()`。

## 3.5 跑第一次之後，抓到自己埋的一個 bug

固定 1:2R 改成 `target_mode="rr"` 之後，信心分數（第 ⑦ 關）裡有一個因子
`rr`——「賠率超過最低要求多少」——悄悄壞掉了：`draw` 模式下賠率會隨市況浮動，
這個因子是有意義的資訊；但固定 1:2R 之後，任何能走到這一步的訊號，賠率**永遠
剛好等於**最低要求（低於就已經在風控關被否決了），所以這個因子的公式
`(rr - min_rr) / 3.0` 算出來永遠是 **0**。結果是：每一筆固定 1:2R 的交易，
分數都被這個因子悄悄扣掉 0.15 的權重，跟市場品質完全無關。

這不是資料造成的，是改動盈虧比模式之後留下的計分邏輯錯誤，我在檢查第一次
跑出來的結果時發現的（`ote_continuation` 完全沒有觸發任何一筆，追進去才發現
是分數普遍被拖低，不是這個劇本真的沒有機會）。修法：固定盈虧比模式下，
只要走到這一步就代表達標，這個因子直接給滿分 1.0——不是因為市場表現好，
是因為「有沒有達到固定門檻」本身就是二元的，不該再用連續公式硬算一個假的
區分度出來。`tests/test_engine.py` 裡加了一個測試鎖住這件事。

**下面第 4 節的數字，是修完這個 bug 之後重新跑出來的。** 修之前的版本
`ote_continuation` 幾乎不會觸發（分數長期不夠），修之後它會大量觸發——
而且觸發之後的表現並不好。這正是這份文件要誠實面對的地方。

## 4. 完整結果（2012-05 至 2022-03，M15，1:2R，計分修正後）

完整報告存在
[`results/backtest_xauusd_m15_2012-2022_real.txt`](../results/backtest_xauusd_m15_2012-2022_real.txt)，
每一筆交易的明細在
[`results/trades_xauusd_m15_2012-2022_real.json`](../results/trades_xauusd_m15_2012-2022_real.json)。

```
bars processed      : 230400
signals generated   : 1068
trades filled       : 525
win rate            : 35.8%  (188W / 334L / 3BE)
expectancy          : -0.160 R per trade
total               : -84.2 R   net $-3,489  (-34.9%)
avg win / avg loss  : +1.13R / -0.89R  (payoff 1.27)
profit factor       : 0.69
max drawdown        : 103.9 R  (40.9% of equity)
max consec losses   : 14
t-stat of expectancy: -3.32  (>2.0 before you believe it — this one clears it)
```

**10 年、525 筆、期望值 -0.160R，t = -3.32。** 這次不是「還不知道」，
是**統計上顯著為負**。跟第 3.5 節那個計分 bug 修好之前的版本（116 筆、
期望值 -0.024R、t=-0.23，接近雜訊）比，差別很大——而這正是那個 bug 造成的：
修之前 `ote_continuation` 幾乎不觸發，修之後它變成樣本數最大、也拖垮整體
最多的劇本。

### 分劇本看

```
judas_reversal     77 trades   44.2% win   +0.053R exp   PF 1.01
silver_bullet      58 trades   31.0% win   -0.188R exp   PF 0.68
ote_continuation  390 trades   34.9% win   -0.198R exp   PF 0.64   totR -77.4
```

`judas_reversal`（假突破反轉）在真實資料上大致打平，樣本數（77）還不到
可以下結論的門檻。`silver_bullet` 和 `ote_continuation` 都是負的，而
`ote_continuation` 的樣本數（390）已經遠遠超過 `docs/METHODOLOGY.md`
建議的 30–50 筆門檻——**這已經不是「樣本不夠、先不下結論」的情況，
是有像樣證據支持「這個劇本在這份資料上是虧錢的」。**

### 我沒有做的事：沒有因為這個結果回頭調 `ote_continuation`

看到 `ote_continuation` 拖垮整體之後，直覺會想調它的參數（放寬折價區要求、
調停損來源、調分數門檻……）讓它在**這份資料**上表現好看一點。
**我沒有這麼做，原因寫在 `docs/METHODOLOGY.md` 第 5 節第 2 條：**
「每次調整都要有機制解釋」——如果我調完之後它變好看了，我沒辦法回答
「為什麼是這個數字」，只能回答「因為調完之後它變好看了」，那就是在對著
考卷背答案，不是在訓練策略。

同樣地，**我也沒有把 `ote_continuation` 從預設設定裡拿掉。** 理由對稱：
拿掉它一樣是根據這份資料的結果去動 L1 規則層，而這份資料本身有三個
第 5 節會列的先天限制（不是今年、時區用猜的、時框是 M15 不是 M5）。
拿掉一個劇本是「規則層」的決定，理論上比調參數更貴（見
`docs/METHODOLOGY.md` 的三層架構表），更不該只靠一份有限制的資料就動手。

**這個結果留在文件裡、留在下面的 walk-forward 裡，原封不動地報給你看。**
它現在是一個很具體的假設，等你拿到真正的 2026 年資料時，第一件事就是
去驗證這個假設還在不在——而不是假裝我看到這個結果的時候什麼都沒做。

## 5. 這些數字能不能拿來相信這個 pipe？

**這次答案要分兩層講，因為「顯著」和「可信」是兩件事：**

- **統計上，這次的負向結果是有支撐的**（t=-3.32、n=525，OOS 六段裡有六段
  同向）。跟修 bug 之前那種「t=-0.23、什麼都證明不了」的雜訊不一樣，
  這次可以說：**在這份資料、這個時框、這個（猜測的）時區設定下，
  現在的預設設定是虧錢的，而且不是運氣。**
- **但這份資料本身撐不起「所以這個 pipe 不能用」的結論**，因為它有三個
  先天限制，跟統計顯著性無關，是資料本身的問題：

  1. **不是今年的資料。** 2022 年 3 月之後黃金經歷了完全不同的宏觀環境
     （升息週期、地緣政治溢價），舊資料上的統計性質不保證延續到今天。
  2. **時區是推測出來的，不是驗證過的。** 如果 killzone 系統性偏移了
     1 小時，`ny_am`／`london` 這些時段過濾器抓到的可能根本不是真正的
     殺戮時段——這足以讓一個原本有效的策略在回測裡看起來是負的。
  3. **M15 不是你設定的 M5。** 進場精度變粗，跟你日內短打的實際用法
     有落差，尤其是 `silver_bullet` 這種設計給更精細時框用的劇本。

**這次測試證明的事，跟修 bug 之前不一樣了**：管線接上真實市場資料之後，
統計行為合理、分數計算的 bug 一被抓到就能造成數量級的差異（116→525 筆）——
**這正說明了為什麼「回測要準」這件事這麼重要：一個看起來很小的計分公式
錯誤，可以讓同一個 setup 從「幾乎不出手」變成「主要虧損來源」。**
這是「管線的測量能力是可信的」的證據；至於「這組預設設定在 2026 年的
黃金市場上會不會賺錢」，答案仍然是：不知道，因為驅動這份負向結果的資料
本身有上面三個問題，必須用真正的 2026 資料重新驗證一次，才能把「這份
資料上是負的」升級或降級成「這個策略是負的」的結論。

## 6. 要怎麼樣才能拿到真正可信的「今年」回測

這個沙盒抓不到即時盤中資料，但你可以，而且只需要幾分鐘：

1. 打開你的 MT4／MT5（或任何有黃金報價的看盤軟體）
2. 「歷史中心」（History Center）→ 選 XAUUSD → M5 或 M15 → 匯出成 CSV
3. 把檔案傳給我（或放進 `ict-gold/data/`，這個資料夾已經設定 `.gitignore`
   排除，不會被誤傳上 GitHub）
4. 我用**同一條管線、同一份設定檔**直接跑：

```bash
python3 -m ictgold backtest --csv 你的檔案.csv --tz <你券商的時區> \
    --config config/xauusd_m15_real_1to2R.json \
    --out results/report_2026.txt --trades results/trades_2026.json
```

匯出時記得選你想要的完整年度範圍，並且**跟我確認一次你的券商時區**
（MT4/MT5 的「工具 → 選項 → 圖表」通常會顯示伺服器時間，或直接問客服）——
這是本文件第 2 節提到的、最容易被忽略卻最致命的一步。

拿到這份資料以後，我才能給你一個**你要求的、可以拿來評估「要不要相信這個
pipe」的、貨真價實的「今年」回測。** 在那之前，任何人（包括我自己）說
「這個策略今年勝率多少」都是在瞎猜。
